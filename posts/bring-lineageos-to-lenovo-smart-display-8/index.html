为 Lenovo Smart Display 8 适配 LineageOS 的记录

  • 2024-08-27
  • Android

适配完大概一个月了，还是系统性记录一下，以免自己忘了，当然如果有人刷到这篇文章，希望能给你一些帮助

文章不是线性的，可以一口气全部看完再上手

从 0 到 1 很困难，不要放弃。自助者天助

软硬件要求

硬件当然是越强越好。为了刷机和调试方便，我是在 Windows 11 里开的 VMware 虚拟机，R7 5800X 16 线程全开 + 16GB 内存，从零开始跑一遍整包 OTA 大概 40-50 分钟 (没开 ccache，开了还能快一些)，考虑到虚拟机损耗，实体机跑起来应该能再快一些

因为适配的 Android 8.1，源码并不大，一套内核 + LineageOS 源码编译完目录大小也不到 200G，好像 150G 都不到，加上系统占用，最少给 200G 就差不多了

软件方面，因为 Android 8.1 还需要用到 Python 2，所以用的 Debian 11。Java 的话，是 OpenJDK 8

最后，强烈建议把源码的改动存到 Git 上，如果嫌 Github 之类公网的麻烦，本地搭一个 Gitea 也不错，否则改动多了，自己都忘记改了什么

对文章里描述不清，或者看不懂的部分，也 请参考 commit 记录，源码在 这里

准备内核源码

这块可以随机应变下。联想官方虽然有给 Lenovo Smart Display 8 开源，但是源码是 Linux 3.10.X 的，机器上的内核版本实际上是 3.18.X。有人在联想官方论坛反馈，不过到现在也没有更新源码

联想有一台相似的机子 (不敢说完全相同，因为拆机之后发现主板丝印实际上是不一样的) 叫做 ThinkSmart View，这台机子开出的源码是 3.18.X 的，因此把它的源码 借过来用

如果你想给没有开源内核的机子编译内核，可以找找有没有相似的机子，然后补一下 dts、驱动、参数试试。实在不行也可以试试 prebuilt 内核，据说 LineageOS 对这块没什么要求，之前看见过一个红米的机子用 prebuilt 内核

适配 device

这块是最复杂的，几乎找不到教程，唯一 的方法是抄别人的 device

不是我说的，LineageOS 官方的 FAQ 就是这么说的

Where are guides so I can port LineageOS to my unsupported device?

  • There are none
  • See what other, similar devices did to get them to work.

提取 vendor proprrietary

就是提取设备官方系统中的 vendor 专有部分，例如摄像头、麦克风、网卡等设备的驱动，例如一些 so 库。这些可能是不开源的，别担心，就连你的设备制造商也没有这些源码，它们也是把第三方厂商提供的成品文件加进 SDK 里编译的

这一步要做的是找出哪些属于设备专有的 blobs，这里可以从相同 SoC 的设备的 device 里抄到，如果找不到，退而求其次，找相同版本的同平台设备。当然即使有相同的 SoC，主板也是不同的，例如它们可能使用不同的摄像头、麦克风，不过通常能提取到最基础的 blobs，足以支持系统启动，在进入系统后遇到摄像头打不开之类的问题，再抓 Log 看看是缺少什么驱动

装好 adb，连接设备，然后找一个与你设备相似的 device。例如这里我找到了联想 P2 的，也是联想的，也是骁龙 625，也是 Android 8.1

打开 proprietary-files.txt，这就是设备专有 blobs 的列表了

打开 device 下的 extract-files.sh，运行这个脚本，就会通过 adb 从设备中提取 blobs 了。在运行之前，修改其中的 DEVICE 和 VENDOR

DEVICE=kuntao
VENDOR=lenovo

因为也是联想的，所以这里 VENDOR 就不改了。DEVICE 改成正确的设备代号，比如 sparrow，这样提取的文件就会存在源码目录下的 vendor/lenovo/sparrow

运行 extract-files.sh，因为是借用别的设备的，列表肯定有出入。遇见 File not found 之类的报错，说明你设备的 firmware 里并没有这个文件，在 proprietary-files.txt 删掉那行。部分带 hash 的提示 Miss match，把 hash 删掉，直到运行 extract-files.sh 可以不报错跑完

剩下的主要靠自己判断了：哪些要删，哪些要加

最后运行 device 下的 setup-makefiles.sh，会在 vendor/lenovo/sparrow 下生成 Makefile，这样 vendor device 就准备好了

修改 device

修改同 SoC 设备的 device 里的参数，例如分区大小、Kernel 参数等。可以参考一下这个 commit

不要一口气抄太多，特别是自己也不理解的参数就别加了。首先需要保证源码可以跑起来，能够生成 OTA Package 和镜像，再考虑修 Bug

完整的 commit 记录可以参考 这里

开始编译

准备好 device 后，回到源码目录执行

source build/envsetup.sh

然后 lunch 选中我们的 device 和构建变体

lunch lenovo_sparrow-eng

使用 eng 变体是为了默认开启 adb 和一些调试功能，要注意选了 eng 就不能用 brunch 了， brunch 会默认选择 userdebug 构建

使用 otapackage 选项构建 eng

make otapackage -j16

也可以单独构建想要的镜像，例如

make systemimage

报错

准备好 device、vendor proprrietary、kernel，理论上现在就可以开始编译了，但是编译 不可能 一次通过。受到各种软件版本的影响，即使是网上搜到的解决方法有时也不那么有用，会看报错至关重要，并且要试着 去看源码

下面记录一些自己遇到并解决的问题

Zygote 不启动

32 位 device 改 64 位时没有修改 core_base.mk 成 core_64_bit.mk 导致

参考 commit

原 device 为 32 位，修改为 64 位后编译，开机停留在 bootanimation，伴随报错，修改回 32 位后编译正常启动

Could not create image space with image file '/system/framework/boot.art'. Attempting to fall back to imageless running. Error was: Cannot relocate image /system/framework/boot.art to : Only the zygote can create the global boot image.

在源码中搜索 Could not create image space with image file，这个报错出现在 art/runtime/gc/space/image_space.cc 的 LoadBootImage 函数中

error = true;
LOG(ERROR) << "Could not create image space with image file '" << image_file_name << "'. "
  << "Attempting to fall back to imageless running. Error was: " << error_msg
  << "\nAttempted image: " << image_name;
break;

error_msg 变量是通过对 CreateBootImage 函数的调用得到的

std::unique_ptr<space::ImageSpace> boot_image_space_uptr = CreateBootImage(
        image_name.c_str(),
        image_instruction_set,
        index > 0,
        &error_msg);

关键在最后一句 Only the zygote can create the global boot image.

在源码中搜索，这个报错同样出现在 art/runtime/gc/space/image_space.cc

static bool ImageCreationAllowed(bool is_global_cache,
                                 const InstructionSet isa,
                                 std::string* error_msg) {
  // Anyone can write into a "local" cache.
  if (!is_global_cache) {
    return true;
  }

  // Only the zygote running as root is allowed to create the global boot image.
  // If the zygote is running as non-root (and cannot write to the dalvik-cache),
  // then image creation is not allowed..
  if (Runtime::Current()->IsZygote()) {
    return CanWriteToDalvikCache(isa);
  }

  *error_msg = "Only the zygote can create the global boot image.";
  return false;
}

报错是因为当前 Runtime 并不是 Zygote 导致的，换句话说就是没有 Zygote 进程

Zygote 是 Android 系统创建新进程的核心进程，负责启动 Dalvik 虚拟机，加载一些必要的系统资源和系统类，启动 system_server 进程，随后进入等待处理 app 应用请求

(以上这段话摘自网络，被引用次数太多，出处未知)

Dalvik 起不来，Android 自然也无法启动

Android 的系统服务和框架都是要运行在 Android Runtime 也就是 Dalvik 虚拟机上的，虚拟机无法启动，则任何 Android 的服务都无法启动

Zygote 服务由 rootdir 下的 init.zygote*.rc 定义，在 init.rc 中被调用

import /init.${ro.zygote}.rc

从 Android 5 开始，Android 支持了 64 位，因此 Zygote 也做了 32 和 64 位的区分

Zygote 有如下 4 种模式，也就是 ro.zygote 可以有如下 4 个值

  1. zygote32: 纯 32 位模式
  2. zygote64: 纯 64 位模式
  3. zygote32_64: 32 位模式为主，64 位模式为辅 (secondary)。即 系统框架是 32 位，但也支持 64 位的应用
  4. zygote64_32: 64 位模式为主，32 位模式为辅 (secondary)。即 系统框架是 64 位，但也支持 32 位的应用

显然针对一般的 64 位设备，zygote64_32 用得比较多

以下是一段默认的 init.zygote32.rc，Zygote 服务的可执行文件是 /system/bin/app_process

service zygote /system/bin/app_process -Xzygote /system/bin --zygote --start-system-server
    class main
    priority -20
    user root
    group root readproc
    socket zygote stream 660 root system
    onrestart write /sys/android_power/request_state wake
    onrestart write /sys/power/state on
    onrestart restart audioserver
    onrestart restart cameraserver
    onrestart restart media
    onrestart restart netd
    onrestart restart wificond
    writepid /dev/cpuset/foreground/tasks

以下是一段默认的 init.zygote64_32.rc。除了 /system/bin/app_process64 的 64 位 Zygote，还定义了一个名为 zygote_secondary 的 32 位 Zygote

service zygote /system/bin/app_process64 -Xzygote /system/bin --zygote --start-system-server --socket-name=zygote
    class main
    priority -20
    user root
    group root readproc
    socket zygote stream 660 root system
    onrestart write /sys/android_power/request_state wake
    onrestart write /sys/power/state on
    onrestart restart audioserver
    onrestart restart cameraserver
    onrestart restart media
    onrestart restart netd
    onrestart restart wificond
    writepid /dev/cpuset/foreground/tasks

service zygote_secondary /system/bin/app_process32 -Xzygote /system/bin --zygote --socket-name=zygote_secondary --enable-lazy-preload
    class main
    priority -20
    user root
    group root readproc
    socket zygote_secondary stream 660 root system
    onrestart restart zygote
    writepid /dev/cpuset/foreground/tasks

Zygote 服务在 init.rc 中是这样被调用的

# It is recommended to put unnecessary data/ initialization from post-fs-data
# to start-zygote in device's init.rc to unblock zygote start.
on zygote-start && property:ro.crypto.state=unencrypted
    # A/B update verifier that marks a successful boot.
    exec_start update_verifier_nonencrypted
    start netd
    start zygote
    start zygote_secondary

on zygote-start && property:ro.crypto.state=unsupported
    # A/B update verifier that marks a successful boot.
    exec_start update_verifier_nonencrypted
    start netd
    start zygote
    start zygote_secondary

on zygote-start && property:ro.crypto.state=encrypted && property:ro.crypto.type=file
    # A/B update verifier that marks a successful boot.
    exec_start update_verifier_nonencrypted
    start netd
    start zygote
    start zygote_secondary

再看 init.rc 中对 zygote-start 的定义，启动 Zygote 的条件是挂载/解密 /data 后

# Now we can mount /data. File encryption requires keymaster to decrypt
# /data, which in turn can only be loaded when system properties are present.
trigger post-fs-data

# Now we can start zygote for devices with file based encryption
trigger zygote-start

看完了 Zygote 启动需要的条件，回到 device 上

用 getprop 一看当前设备的 ro.zygote 值，居然还是 zygote32，怪不得启动不了 64 位系统

如果直接在 device 的 Makefile 里覆盖 ro.zygote 属性，会出现报错 “cannot assign to readonly variable”

这是因为这个属性并不需要手动指定，它已经定义在 build/make/target/product 下的 Makefile 中指定，并在 device 中 include

检查 device，发现了对 build/make/target/product 下的 Makefile 的引用

$(call inherit-product, $(SRC_TARGET_DIR)/product/core_base.mk)

查看 core_base.mk，其又引用了 core_minimal.mk，其中定义了

PRODUCT_DEFAULT_PROPERTY_OVERRIDES += \
    ro.zygote=zygote32
PRODUCT_COPY_FILES += \
    system/core/rootdir/init.zygote32.rc:root/init.zygote32.rc

再查看同一目录下的 core_64_bit.mk

# Copy the 64-bit primary, 32-bit secondary zygote startup script
PRODUCT_COPY_FILES += system/core/rootdir/init.zygote64_32.rc:root/init.zygote64_32.rc

# Set the zygote property to select the 64-bit primary, 32-bit secondary script
# This line must be parsed before the one in core_minimal.mk
PRODUCT_DEFAULT_PROPERTY_OVERRIDES += ro.zygote=zygote64_32

问题解决，只需要把 device 中对 core_base.mk 的引用改成 core_64_bit.mk 即可

在 Google 的文档里发现了对这个问题的解释：提前装载分区 | Android Open Source Project (中文翻译得不是那么准确，还是建议看英文的)

支持 Treble 的设备必须启用第一阶段装载，以确保 init 可以加载分布在 system 和 vendor 分区的 安全增强型 (SELinux) 政策 Fragment。此访问权限还可实现在内核启动后尽快加载内核模块。

如需执行提前装载，Android 必须有权访问模块所在的文件系统。Android 8.0 及更高版本支持在 init 的第一阶段（即初始化 SElinux 之前）装载 /system、/vendor 或 /odm。

Treble 部分就不再详细介绍了，简单来说就是将 Android 系统本身与硬件供应商的代码隔离，并提供了一个统一的接口供 Android 访问硬件供应商部分代码，从此开发者就只需要更新 Android 系统本身，并通过统一接口连接 Android 和硬件供应商部分代码

在 Android 9 及更低版本中，设备可以使用 设备树叠加层 (DTO) 为提前装载的分区指定 fstab 条目

也就是说，当前 /system 和 /vendor 的 fstab 是被定义在 Device Tree 中的，在 kernel 源码的 dts 中，如下

firmware {

		android {
			compatible = "android,firmware";

			fstab {
				compatible = "android,fstab";

				vendor {
					compatible = "android,vendor";
					dev = "/dev/block/platform/soc/7824900.sdhci/by-name/vendor";
					type = "ext4";
					mnt_flags = "ro,barrier=1,discard";
					fsmgr_flags = "wait";
					status = "ok";
				};

				system {
					compatible = "android,system";
					dev = "/dev/block/platform/soc/7824900.sdhci/by-name/system";
					type = "ext4";
					mnt_flags = "ro,barrier=1,discard";
					fsmgr_flags = "wait";
					status = "ok";
				};
			};
		};
	};

这就解释了为什么 fstab 中没有 /system 和 /vendor，却依旧可以正常挂载这两个分区

Data 加解密

全盘加密是在 Android 4.4 版中引入的，不过 Android 5.0 中又引入了以下新功能

  • 新增了快速加密方式，这种加密方式只会对数据分区中已使用的分块进行加密，以免首次启动用时过长。目前只有 EXT4 和 F2FS 文件系统支持快速加密。
  • 添加了 forceencrypt fstab 标记，以便在首次启动时进行加密。
  • 添加了对解锁图案和无密码加密的支持。
  • 添加了由硬件支持的加密密钥存储空间，该空间使用可信执行环境（TEE，例如 TrustZone）的签名功能。如需了解详情，请参阅 存储已加密的密钥。

最后关闭了自动加密，参考 commit

为了启用硬件加密，需要在 device 里加入如下配置

    # Encryption
TARGET_HW_DISK_ENCRYPTION := true
TARGET_LEGACY_HW_DISK_ENCRYPTION := true
TARGET_CRYPTFS_HW_PATH := vendor/qcom/opensource/cryptfs_hw

    其中 TARGET_CRYPTFS_HW_PATH 需要指向高通的 cryptfs_hw 模块

  • device.mk

    # HW crypto
PRODUCT_PACKAGES += \
    vendor.qti.hardware.cryptfshw@1.0-service-qti.qsee

    除此之外，还需要 qseecomd 及其依赖

在添加完加解密所需的依赖后，还需要在 fstab.qcom 分区表中设置哪些分区可以被加密

在需要加密的分区的 fs_mgr_flags 字段里添加 flag，可以是如下值

  • forceencrypt 当前分区未加密，但要求在首次启动后强制加密
  • encryptable 当前分区未加密，用户可以在设置中手动为其加密

不装载 /data

fstab 分区表有误导致

这个问题卡了很久，期间一直没找对关键 Log，记录下自己走的弯路

表现为设置强制加密 forceencrypt 后，开机 vold 和 qseecomd 均可以启动，但不调用 CryptFS 开始加密 /data，系统也不会继续启动 Zygote

去除强制加密后，故障依旧，可以挂载 /data，/data 有文件释放，但系统并无进一步动作

还记得前面分析 [Zygote 启动流程](#Zygote 不启动) 的 init.rc 时，有一个属性叫做 ro.crypto.state，当这个属性被设置时，Zygote 才会启动

这个属性共有 3 种状态

  • unencrypted: 已解密
  • unsupported: 不支持加密 (未启用)
  • encrypted: 已加密，这里是结合 FBE 使用
# It is recommended to put unnecessary data/ initialization from post-fs-data
# to start-zygote in device's init.rc to unblock zygote start.
on zygote-start && property:ro.crypto.state=unencrypted
    # A/B update verifier that marks a successful boot.
    exec_start update_verifier_nonencrypted
    start netd
    start zygote
    start zygote_secondary

on zygote-start && property:ro.crypto.state=unsupported
    # A/B update verifier that marks a successful boot.
    exec_start update_verifier_nonencrypted
    start netd
    start zygote
    start zygote_secondary

on zygote-start && property:ro.crypto.state=encrypted && property:ro.crypto.type=file
    # A/B update verifier that marks a successful boot.
    exec_start update_verifier_nonencrypted
    start netd
    start zygote

运行 getprop ro.crypto.state，发现现在没有这个属性，那 ro.crypto.state 的值是谁设置的？

在源码中搜索，发现 /system/core/init/builtins.cpp 中有对这个属性进行 property_set

进入 queue_fs_event() 函数

/* Queue event based on fs_mgr return code.
 *
 * code: return code of fs_mgr_mount_all
 *
 * This function might request a reboot, in which case it will
 * not return.
 *
 * return code is processed based on input code
 */

static int queue_fs_event(int code) {
    int ret = code;
    
    if (code == FS_MGR_MNTALL_DEV_NEEDS_ENCRYPTION) { // 分区强制加密，但当前未加密 (forceencrypt)
        ActionManager::GetInstance().QueueEventTrigger("encrypt"); // 触发 encrypt，在 init.*.rc 里，后面会说
    } else if (code == FS_MGR_MNTALL_DEV_MIGHT_BE_ENCRYPTED) { // 分区可能已经加密，加密类型为 block
        property_set("ro.crypto.state", "encrypted");
        property_set("ro.crypto.type", "block");
        ActionManager::GetInstance().QueueEventTrigger("defaultcrypto"); // 触发 defaultcrypto
    } else if (code == FS_MGR_MNTALL_DEV_NOT_ENCRYPTED) { // 分区未加密 (encryptable)
        property_set("ro.crypto.state", "unencrypted");
        ActionManager::GetInstance().QueueEventTrigger("nonencrypted"); // 触发 nonencrypted
    } else if (code == FS_MGR_MNTALL_DEV_NOT_ENCRYPTABLE) { // 分区不支持加密
        property_set("ro.crypto.state", "unsupported");
        ActionManager::GetInstance().QueueEventTrigger("nonencrypted"); // 触发 nonencrypted
    } else if (code == FS_MGR_MNTALL_DEV_NEEDS_RECOVERY) {
        /* Setup a wipe via recovery, and reboot into recovery */
        PLOG(ERROR) << "fs_mgr_mount_all suggested recovery, so wiping data via recovery.";
        const std::vector<std::string> options = {"--wipe_data", "--reason=fs_mgr_mount_all" };
        reboot_into_recovery(options);
        return 0;
        /* If reboot worked, there is no return. */
    } else if (code == FS_MGR_MNTALL_DEV_FILE_ENCRYPTED) {
        if (e4crypt_install_keyring()) {
            return -1;
        }
        property_set("ro.crypto.state", "encrypted");
        property_set("ro.crypto.type", "file");

        // Although encrypted, we have device key, so we do not need to
        // do anything different from the nonencrypted case.
        ActionManager::GetInstance().QueueEventTrigger("nonencrypted");
    } else if (code == FS_MGR_MNTALL_DEV_IS_METADATA_ENCRYPTED) {
        if (e4crypt_install_keyring()) {
            return -1;
        }
        property_set("ro.crypto.state", "encrypted");
        property_set("ro.crypto.type", "file");

        // defaultcrypto detects file/block encryption. init flow is same for each.
        ActionManager::GetInstance().QueueEventTrigger("defaultcrypto");
    } else if (code == FS_MGR_MNTALL_DEV_NEEDS_METADATA_ENCRYPTION) {
        if (e4crypt_install_keyring()) {
            return -1;
        }
        property_set("ro.crypto.type", "file");

        // encrypt detects file/block encryption. init flow is same for each.
        ActionManager::GetInstance().QueueEventTrigger("encrypt");
    } else if (code > 0) {
        PLOG(ERROR) << "fs_mgr_mount_all returned unexpected error " << code;
    }
    /* else ... < 0: error */

    return ret;
}

函数通过几个 if 判断来设置 ro.crypto.state

下面是两种常见的情况

  • FS_MGR_MNTALL_DEV_NEEDS_ENCRYPTION: 分区强制加密，但当前未加密 (fs_mgr_tag 含有 forceencrypt)
  • FS_MGR_MNTALL_DEV_NOT_ENCRYPTED: 分区未加密 (fs_mgr_tag 含有 encryptable)

显然，当我们配置强制加密的时候，需要得到的返回值是 FS_MGR_MNTALL_DEV_NEEDS_ENCRYPTION

如果不加密，则是 FS_MGR_MNTALL_DEV_NOT_ENCRYPTED

函数前面的注释写道

return code of fs_mgr_mount_all

即通过 fs_mgr_mount_all() 函数的返回值，来确定 ro.crypto.type

// Check to see if a mountable volume has encryption requirements
static int handle_encryptable(const struct fstab_rec* rec)
{
    /* If this is block encryptable, need to trigger encryption */
    if (needs_block_encryption(rec)) {
        if (umount(rec->mount_point) == 0) {
            return FS_MGR_MNTALL_DEV_NEEDS_ENCRYPTION;
        } else {
            PWARNING << "Could not umount " << rec->mount_point
                     << " - allow continue unencrypted";
            return FS_MGR_MNTALL_DEV_NOT_ENCRYPTED;
        }
    } else if (should_use_metadata_encryption(rec)) {
        if (umount(rec->mount_point) == 0) {
            return FS_MGR_MNTALL_DEV_NEEDS_METADATA_ENCRYPTION;
        } else {
            PERROR << "Could not umount " << rec->mount_point << " - fail since can't encrypt";
            return FS_MGR_MNTALL_FAIL;
        }
    } else if (rec->fs_mgr_flags & (MF_FILEENCRYPTION | MF_FORCEFDEORFBE)) {
        LINFO << rec->mount_point << " is file encrypted";
        return FS_MGR_MNTALL_DEV_FILE_ENCRYPTED;
    } else if (fs_mgr_is_encryptable(rec)) {
        return FS_MGR_MNTALL_DEV_NOT_ENCRYPTED;
    } else {
        return FS_MGR_MNTALL_DEV_NOT_ENCRYPTABLE;
    }
}

这里又调用了 needs_block_encryption() 函数，用于检查当前 fstab 条目是否需要加密

static bool needs_block_encryption(const struct fstab_rec* rec)
{
    if (device_is_force_encrypted() && fs_mgr_is_encryptable(rec)) return true;
    if (rec->fs_mgr_flags & MF_FORCECRYPT) return true;
    if (rec->fs_mgr_flags & MF_CRYPT) {
        /* Check for existence of convert_fde breadcrumb file */
        char convert_fde_name[PATH_MAX];
        snprintf(convert_fde_name, sizeof(convert_fde_name),
                 "%s/misc/vold/convert_fde", rec->mount_point);
        if (access(convert_fde_name, F_OK) == 0) return true;
    }
    if (rec->fs_mgr_flags & MF_FORCEFDEORFBE) {
        /* Check for absence of convert_fbe breadcrumb file */
        char convert_fbe_name[PATH_MAX];
        snprintf(convert_fbe_name, sizeof(convert_fbe_name),
                 "%s/convert_fbe", rec->mount_point);
        if (access(convert_fbe_name, F_OK) != 0) return true;
    }
    return false;
}

int fs_mgr_is_encryptable(const struct fstab_rec *fstab)
{
    return fstab->fs_mgr_flags & (MF_CRYPT | MF_FORCECRYPT | MF_FORCEFDEORFBE);
}

SELinux avc

权限配置不够全面导致

开机之后依旧无法加密 /data，并很快重启，有两个很明显的 SELinux avc 报错

Could not load libQSEEComAPI.so

enabling encryption after framework is shutdown, no data changed, restarting system

avc: denied { execute } for path="/vendor/lib64/libQSEEComAPI.so" dev="mmcblk0p45" ino=128 scontext=u:r:vold:s0 tcontext=u:object_r:vendor_file:s0 tclass=file permissive=0

avc: denied { execute } for path="/vendor/lib64/libQSEEComAPI.so" dev="mmcblk0p45" ino=128 scontext=u:r:vold:s0 tcontext=u:object_r:vendor_file:s0 tclass=file permissive=0

SELinux 报错的格式如下

denied {权限的名称} for path=“文件路径” dev=“mmcblk0p45” ino=128 scontext=u:r:触发 SELiunx 的进程名称:s0 tcontext=u:object_r:该进程对什么组的文件缺少权限 tclass=文件类型 permissive=0

按照这个格式，对报错进行分析

  • 进程 vold 缺少对 vendor_file 组下的文件 /vendor/lib64/libQSEEComAPI.so 的 execute 权限

知道谁对谁缺少什么权限后，在 device 下 sepolicy 目录新建 vold.te

allow vold vendor_file:file { getattr open read execute };

这样就添加好了 SELinux 权限

通过命令 mmma system/sepolicy/ 单独编译 SELinux，然后 make otapackage 或者单独打包 system 和 vendor 即可生效
